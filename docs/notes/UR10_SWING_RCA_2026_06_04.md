# UR10 transit-swing — root-cause analysis (2026-06-04)

Tool: `scripts/qa/scene_eyes.py` (virtual-eyes probe — live EE pose+quat, joint angles,
tool-length/elongation, **exact cuRobo planned trajectories** per segment + seed diag).

## Symptom (Anton, viewport)
Arm picks, then "small steps", reaches across in an arc, hits near-singularity, **turns around /
flips to approach from the other side** (the "swing"), + rubber "elongation" on drop, + a non-
rendering middle section between flange and cup.

## Root cause — GEOMETRICALLY FORCED IK-branch flip (proven, not tuned)
CP-69: UR10 base at (0,0,0.75), picks a cube far BEHIND (x=-1.0) off a belt, delivers to a bin in
FRONT (x=+0.5), tool **locked pointing down** through transit. The pick config and the bin config
sit on different IK branches; the transit must cross config-space discontinuity at x≈0 (front-center).

Exact cuRobo data (eyes plan-capture): the transit plan to goal [0.14,-0.43,1.27] is **plan#7,
max joint sweep 223°** (elbow 223°, wrist_1 198°, shoulder_pan 107°). Branch-continuity test
(closest of 16 IK seeds to current config): bestd jumps 1.5 rad → **11.5 rad at plan#7** → there is
**no continuous IK solution** across the crossing. The flip is kinematically unavoidable for this
layout + down-lock.

## Levers tested (all measured with scene_eyes; verified non-stale: 4 distinct cached planners)
| Lever | transit sweep | verdict |
|---|---|---|
| arc ON (baseline) | plan#7 = 223° | 11 plans, elongation +48mm |
| arc OFF | plan#4 = 180° | 7 plans; elongation WORSE (+150mm, faster move); NOT the root |
| more seeds (ik48/tj8) | plan#7 = 241° | WORSE; violent playback (15 m/s, +1335mm); seed_rank 0→5 |
| plan_cspace (joint goal) | 223° | cspace ran (dbg-confirmed) but IK goal itself is the flipped config → same |
| cspace + closest-of-16 IK | 223° | closest IK solution is 11.5 rad away → no continuous branch → same |
| orientation_tolerance 1.0 | 223° | no change — loose TOLERANCE ≠ incentive to leave down-orientation |

Conclusion: the swing is **not** a planner-tuning bug. No cuRobo setting avoids it because no
continuous IK path exists for far-behind-pick → front-bin with a down-locked tool.

## Real levers (scene/task or constraint-relaxation) — NEXT
1. **Position-only transit** (remove the orientation goal mid-air; pin orientation only at pick/place).
   Only planner-level lever left, and it ALSO removes the "cup always points down" cheat. UNTESTED.
2. Reposition base / bin so pick + place share an IK branch (no front-center crossing). Task-level.
3. Let the belt carry the cube closer before picking (pick at less-extreme x). Task-level.

## Separate issues (not the swing)
- **Elongation** = kinematic-follower lag (cone is a dynamic body FixedJoint'd to a kinematic
  follower teleported to ee FK; fast moves → it lags). Speed-correlated (+48mm @2.8m/s → +150mm
  @3.3m/s → +1335mm @15m/s). Fix: stiffer/faster follower tracking or cap tool speed.
- **Non-rendering middle**: the VisShaft cylinder (fixed 0.075m, child of the cone) doesn't span
  the flange↔cone gap when the cone separates. Render-only.

## Update — position-only lever tested (broke the solve)
`ToolPoseCriteria.track_position()` applied to the trajopt solver (gate `_ur10_pos_only`) made
EVERY plan FAIL -> arm no-op ("planning failed for /World/Cube_1", all joints 0°). track_position
conflicts with plan_pose's pose-goal + use_implicit_goal + success metric. So position-only is the
right IDEA but needs proper integration (position-only IK seed + plan_cspace, or a position-only
success tolerance), NOT a one-line criteria swap. => the swing has NO quick planner fix; recommend
scene/task-level (reposition base/bin so pick+place share a branch; or belt-carry the cube closer)
or a dedicated position-only-transit implementation.

## DECISIVE confirmation — the swing is CP-69-specific (far-behind pick), not a UR10/cuRobo problem
Ran scene_eyes on the other UR10 templates (default flags):
| template | pick x | worst transit plan sweep | flip |
|---|---|---|---|
| CP-69 | -1.0 | 223° (plan#7, front-center crossing) | YES |
| CP-70 | -0.5 | 41° (smooth arc, y stays high then curves) | no |
| CP-75 | -0.5 | 42° | no |
CP-70/75 pick at x=-0.5 and arc smoothly around in ONE IK branch (max 42°). CP-69 triggers the pick
while the cube is still ~1m BEHIND the base (x=-1.0); the transit to the front bin then must cross
the front-center config-space discontinuity -> the 223° flip. So: NOT a planner bug, NOT a UR10
limitation — CP-69 simply picks too far back.

## RECOMMENDATION (Anton's call — changes CP-69 task timing)
Primary: let the conveyor carry the cube closer (trigger the pick at ~x=-0.5, where CP-70/75 are
clean) instead of at x=-1.0. Validated indirectly by CP-70/75 being flip-free at x=-0.5. This is a
template/sensor-position change (task semantics), so it's Anton's decision.
Alternatives: reposition the UR10 base so x=-1.0 and x=+0.5 share a branch; or a proper position-only
-transit integration (track_position alone breaks the solve — needs position-only IK + cspace).
Separate, independent: suction elongation (follower-lag, speed-correlated) + VisShaft non-render.

## Metric correction — it's a BRANCH DISCONTINUITY, not a singularity (verified)
Tested the principled per-config metric (Jacobian condition number via SVD, cuRobo Kinematics
compute_jacobian) at the exact configs:
  flip  config: cond=6.4  manip=0.114   <- BETTER conditioned than clean
  clean config: cond=8.0  manip=0.053
  home:         cond=6.1  manip=0.262
=> The flip config is NOT near-singular. Endpoint condition-number / manipulability (what the
diagnose/ module's `manipulability` metric AND the agents' proposed endpoint metric use) does NOT
discriminate the swing. The swing is a BRANCH DISCONTINUITY: two well-conditioned configs ~11.5 rad
apart (elbow +1.98 -> -1.91, crossing elbow-straight MID-PATH). Endpoints fine; the PATH crosses the
singular region.
=> A real plannability check must be PATH-AWARE: either (a) max planned joint-sweep across the
transit (PROVEN discriminator: 223° flip vs 42° clean — scene_eyes already measures it), or (b) min
manipulability / max condition-number sampled ALONG the planned trajectory (not at endpoints).
=> Ties to TEMPLATES: a pre-flight "plan the transit, flag if max joint-sweep > ~90-120°" check can
scan the template library to flag CP-69-style problematic pick geometry. Build as a template-
validation increment, not a new architecture. Full LLM-telemetry exposure + per-scene datalogging =
the separate "close the diagnose loop" expansion direction (deferred).
