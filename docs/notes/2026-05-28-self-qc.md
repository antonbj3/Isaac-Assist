## Commit `cee5cfcb` — USD-color introspection fast path (sensors.py)

**Verdict: NEEDS-PATCH** (functionally correct happy-path; silent-fail and one logic gap)

### Correctness

- **Diff confirms commit message**: 118 lines added immediately before VLM path in `_handle_add_vision_classifier_gate` at sensors.py:615-731 — matches description.
- **Label tokenisation is narrow** (sensors.py:633-636): only strips `" cube"` / `" box"` suffix. Labels like `"red object"`, `"red item"`, `"red block"`, `"red 0"` will NOT tokenize and fast-path correctly skips them (falls through to VLM). Verified safe.
- **`_color_shaped` precondition** (line 637): requires ALL `class_labels` to be color-tokens. Single non-color label → entire fast path skipped → VLM fallback. Correct.
- **Material walk** (lines 645-677): uses `UsdShade.MaterialBindingAPI(p).GetDirectBindingRel()`. This only finds DIRECTLY-bound materials on the cube prim itself. Materials bound via child Mesh prim (common with USD references — `/World/Cube_0/Geom/Mesh` carries the binding, not the Xform at `/World/Cube_0`) yield `rel.GetTargets()` empty → `color=None` → fast path bails to VLM. Safe but means fast-path may rarely fire for non-trivial cube assets. Could be improved by also walking `UsdShade.MaterialBindingAPI.ComputeBoundMaterial()` which traverses inheritance and child prims.
- **Multiple instancing**: a single OmniPBR material bound to multiple cubes with overrides on `diffuse_color` per-instance is NOT supported here — we read the shader-prim input value, which is the shared (un-overridden) value. All cubes would resolve to the same color. (Likely not an issue for current templates, but worth knowing.)
- **Diffuse-input naming** (line 666): tries `diffuse_color`, `diffuseColor`, `diffuse_color_constant`, `baseColor`, `base_color`. This covers OmniPBR (`diffuse_color_constant`), UsdPreviewSurface (`diffuseColor`), and Lula `base_color`. Reasonable.
- **Output parsing** (line 685): scans output lines for both markers on the SAME line. `print(... json.dumps(out) ...)` produces single-line output (no newlines in compact JSON of a flat dict). Safe.
- **`_color_data` empty case**: if `exec_sync` returns no output or markers missing, `_color_data = {}`. Then `for cp in cube_paths: rgb = _color_data.get(cp)` → `None` → `_all_have_color = False` → fast path bails. Correct fallback.

### Edge cases

1. **Silent exception path on `exec_sync` returns non-OK** (line 681-690): if `exec_sync` succeeds at the RPC level but the script *inside* raises (e.g. `omni.usd` not available), `r.get("output")` likely contains the traceback as text, no markers found, `_color_data={}`, fast path bails to VLM. OK.
2. **`destination_map` fuzzy match** (line 716-718): `if k.lower() in lbl.lower() or lbl.lower() in k.lower()`. With short tokens like `"red"`, can falsely match `"red bin"` AND `"prepared red"` AND `"covered"` (contains `"red"`). Could pick wrong destination on bad keys. Worth tightening to exact-token-match.
3. **`!r` interpolation of `cube_paths` into f-string**: `cube_paths!r` produces Python literal (`['cube_a', 'cube_b']`). Safe — `exec_sync` parses it as Python.

### Backward compat

- Falls through to existing VLM path verbatim when fast-path bails. No regression risk for non-color-labeled templates.

### Suggested patches (not applied)

- (Minor) Fuzzy destination-map match should require token-boundary equality, not substring containment, to avoid mismatches with labels like `"red"` matching destinations keyed `"sorted_red"` and `"cover_red"`.
- (Optional) Add `UsdShade.MaterialBindingAPI.ComputeBoundMaterial()` as a fallback after `GetDirectBindingRel()` to handle child-mesh bindings.

**Consequence**: in a dual-arm template (e.g. roco-bimanual-assembly):
1. Robot A install → registers untagged `"native_pp"` hook for Robot A.
2. Robot B install → unregister-tagged `"native_pp_World_FrankaB"` (no match — never registered tagged) → unregister-untagged `"native_pp"` (REMOVES Robot A's hook) → registers untagged `"native_pp"` for Robot B.

Result: subscription is per-robot (good), but scene-reset hook is still single-tenant. Robot A's reset hook is silently torn down when Robot B installs. The dual-PPC fix is INCOMPLETE — the subscription works concurrently, but the reset-on-stop path will fire only for the most-recently-installed robot.

### Substring trap (commit message acknowledges path-sanitization concern)

`_ROBOT_TAG = ROBOT_PATH.replace("/", "_").strip("_")`. Then `if ... _ROBOT_TAG in _a:`.

- `/World/FrankaLeft` → TAG=`World_FrankaLeft`
- `/World/FrankaRight` → TAG=`World_FrankaRight`

`"World_FrankaLeft" in "..._World_FrankaRight"` → FALSE. Safe for bimanual case.

But:
- `/World/Robot` → TAG=`World_Robot`
- `/World/Robot2` → TAG=`World_Robot2`

`"World_Robot" in "..._World_Robot2"` → **TRUE**. So Robot 1's install WILL tear down Robot 2's subs (cross-mode sweep), and vice versa. Likely doesn't bite current templates (verified roco-bimanual uses Left/Right), but is a latent foot-gun. Fix would be to suffix subs with `_END` marker or use exact match (`endswith("_" + _ROBOT_TAG)`).

### Backward compat

- Single-robot templates: subscription teardown still works (single TAG, single sub). Untagged legacy unregister still fires → clean teardown. Verified safe.
- Mixed legacy+new: `unregister(_hn)` is kept as fallback for hooks left by old installs. Good.

### Suggested patches (not applied)

1. **Critical for true dual-PPC**: register scene-reset hooks under tagged names too:
   - At line 3116: change `register("native_pp", ...)` to `register("native_pp_" + _ROBOT_TAG, ...)`
   - At line 3930: same for `spline_pp`
   - At line 6054: same for `diffik_pp`
   - At line 6557: same for `osc_pp`
   - Verify each variant's reset-hook closure uses `_ROBOT_TAG` correctly.
2. **Substring trap**: change guard from `_ROBOT_TAG in _a` to `_a.endswith("_" + _ROBOT_TAG)`. This is a minimal, mechanical change to all 5 variants.

### Risk for next sweep
